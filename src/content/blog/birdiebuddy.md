저는 골프를 아주아주 좋아합니다.

연습을 하다가 허리도 크게 다칠 만큼 열심히 합니다.

그리고 개발은 아마도 좋아합니다. 애증의 관계죠.

좋아하는 것과 잘하는 것은 별개지만 그래도 열심히 하려고 **"노력"**은 합니다.

보통 취미가 두 개 있으면 각각 즐기면 됩니다.

그런데 개발자의 취미는 가끔 서로 합쳐집니다.

> "내 골프 기록을 직접 관리하는 앱을 만들어보면 어떨까?"

여기까지는 꽤 괜찮은 생각이었습니다.

그렇게 시작한 프로젝트가 **BirdieBuddy**입니다.

처음 목표는 정말 단순했습니다.

라운드를 기록하고,

홀별 스코어를 저장하고,

GIR이나 Fairway Hit 같은 통계를 모아서,

내 골프가 실제로 나아지고 있는지 확인하는 것.

쉽게 말하면 **나를 위한 골프 기록 앱**을 만들고 싶었습니다.

그런데 앱을 만들기 시작하자 아주 기본적인 문제가 하나 생겼습니다.

## 골프장 데이터는 어디서 가져오지?

라운드를 기록하려면 당연히 어느 골프장에서 쳤는지 알아야 합니다.

처음에는 골프장 이름 정도만 있으면 되는 줄 알았습니다.

하지만 실제 라운드 데이터를 제대로 기록하려고 보니 필요한 정보가 생각보다 많았습니다.

골프장에는 코스가 있고,

코스에는 여러 Tee가 있고,

Tee마다 Course Rating과 Slope Rating이 다르고,

각 홀에는 Par와 거리가 있습니다.

결국 제가 원했던 데이터는 대략 이런 구조였습니다.

```text
Golf Club
   │
   └── Course
          │
          └── Tee
               ├── Course Rating
               ├── Slope Rating
               └── Holes
                    ├── Par
                    ├── Distance
                    └── Stroke Index
```

제가 자주 가는 골프장 몇 개만 직접 입력할 수도 있었습니다.

그런데 BirdieBuddy를 제대로 만들어보려면 결국 더 많은 골프장 데이터가 필요할 것 같았습니다.

## 그래서 일단 API부터

처음부터 웹사이트를 긁을 생각은 없었습니다.

가능하다면 API를 사용하는 게 훨씬 깔끔합니다.

그래서 가장 먼저 뉴질랜드 골프 데이터를 다루는 **GolfNZ 쪽 API**를 찾아봤습니다.

처음 생각했던 구조는 아주 아름다웠습니다.

```text
GolfNZ API
     ↓
Course Data
     ↓
BirdieBuddy
```

API에서 골프장 데이터를 받아서 저장하면 끝이라고만 생각한 채 일단 시작했습니다.

하지만 언제나 세상은 제가 원하는 대로 움직여주지 않죠.

제가 BirdieBuddy에서 원했던 것처럼 뉴질랜드 전역의 골프장과 코스, Tee 데이터를 자유롭게 가져오는 용도로 사용하기에는 제약이 있었습니다.

인증과 접근 범위 등의 문제가 있었고,

결국 제가 원하는 방식으로 바로 사용할 수는 없었습니다.

그래도 여기서 포기할 이유는 없었습니다.

세상에는 Golf Course API가 하나만 있는 것도 아니니까요.

## 그럼 다른 Golf API를 쓰면 되겠지

그래서 다른 Golf Course API들도 찾아보기 시작했습니다.

전 세계 골프장 데이터를 제공하는 API는 생각보다 여러 개 있었습니다.

골프장을 검색할 수도 있고,

코스 정보를 제공하는 곳도 있었고,

어떤 API는 Tee Box나 Course Rating, Slope 같은 정보까지 가지고 있었습니다.

처음에는 생각했습니다.

> "아, 그냥 이걸 쓰면 되겠네."

그래서 실제로 몇 가지 API를 연결해보고 뉴질랜드 골프장들을 검색해봤습니다.

그런데 또 다른 문제가 생겼습니다.

**뉴질랜드 데이터가 생각보다 부족했습니다.**

유명한 골프장은 잘 나오는 경우도 있었지만,

제가 찾는 골프장이 없기도 했고,

골프장은 있어도 Tee 정보가 부족하거나,

홀별 데이터가 완전하지 않은 경우도 있었습니다.

제가 필요했던 것은 단순히 이런 정보가 아니었습니다.

```text
Akarana Golf Club
Auckland, New Zealand
```

이 정도라면 비교적 쉽게 구할 수 있습니다.

하지만 BirdieBuddy에서 실제 라운드를 기록하려면 조금 더 자세한 정보가 필요했습니다.

예를 들면 이런 식입니다.

```text
Akarana Golf Club
└── Course
    └── BLUE C
        ├── Course Rating: 69.8
        ├── Slope Rating: 124
        ├── Total Par: 70
        │
        ├── Hole 1
        │   ├── Par: 5
        │   └── Distance: 410m
        │
        ├── Hole 2
        │   ├── Par: 4
        │   └── Distance: 264m
        │
        └── ...
```

골프장 위치를 보여주는 앱이었다면 기존 API로 충분했을지도 모릅니다.

하지만 저는 실제 라운드를 기록할 수 있을 정도로 자세한 **뉴질랜드 코스 데이터**가 필요했습니다.

API 하나를 찾으면 문제가 해결될 줄 알았는데,

몇 개를 찾아보고 나니 오히려 한 가지가 확실해졌습니다.

> "내가 필요한 데이터는 여기 다 없구나."

## 결국 원본으로 돌아왔다

그러다 다시 **Golf New Zealand** 웹사이트를 봤습니다.

제가 찾던 데이터가 거기 있었습니다.

뉴질랜드 골프 클럽,

코스,

Tee,

Course Rating,

Slope Rating,

그리고 홀별 정보까지.

API로 깔끔하게 가져오지는 못했지만,

**웹사이트에는 있었습니다.**

잠시 고민했습니다.

그리고 개발하다 보면 가끔 등장하는 결론에 도달했습니다.

> "API로 못 가져오면... 페이지에서 가져오면 되지 않을까?"

그렇게 **Python과 Playwright**를 꺼냈습니다.

```text
GolfNZ API 시도
       ↓
원하는 방식으로 사용하기 어려움
       ↓
다른 Golf API 탐색
       ↓
뉴질랜드 데이터 부족
       ↓
Golf New Zealand 웹사이트
       ↓
"여기에는 다 있네?"
       ↓
Python + Playwright
       ↓
스크래핑
       ↓
BirdieBuddy
```

**API를 찾다가 브라우저 자동화를 만들게 됐습니다.**

평소에는 계획적인데 프로젝트만 시작하면 사람이 왜 이렇게 즉흥적으로 변할까요..

## Playwright로 하나씩 가져오기

이제 목표는 명확했습니다.

Golf New Zealand 웹사이트에 있는 데이터를 BirdieBuddy에서 사용할 수 있는 형태로 가져오는 것.

스크래퍼는 Python으로 작성하고,

브라우저 자동화에는 **Playwright**를 사용했습니다.

페이지를 열고,

클럽을 찾고,

각 클럽의 코스를 확인하고,

Tee와 Course Rating, Slope Rating,

그리고 각 홀의 Par와 거리 같은 정보를 가져오는 방식입니다.

전체 흐름은 대략 이렇습니다.

```text
Golf New Zealand
        ↓
   Club 목록 수집
        ↓
   Course 확인
        ↓
 Tee / Rating / Slope
        ↓
   Hole 1 ~ 18
        ↓
Par / Distance / Stroke Index
        ↓
      JSON
        ↓
   BirdieBuddy
```

처음부터 전국 골프장을 전부 돌린 것은 아닙니다.

일단 하나의 골프장으로 테스트했습니다.

페이지 구조를 제대로 읽을 수 있는지,

제가 원하는 데이터가 들어오는지,

JSON으로 변환했을 때 구조가 괜찮은지 확인해야 했습니다.

그중 하나가 **Akarana Golf Club**이었습니다.

가져온 데이터는 이런 식이었습니다.

```text
Akarana Golf Club

Tee: BLUE C
Course Rating: 69.8
Slope Rating: 124
Total Par: 70

Hole 1
Par: 5
Distance: 410m

Hole 2
Par: 4
Distance: 264m
```

처음 이 데이터가 제대로 들어왔을 때는 꽤 기분이 좋았습니다.

그리고 결국엔

## Courses: 345 saved.

전국 골프장을 모두 돌렸습니다.

Golf New Zealand의 데이터를 하나씩 확인하고,

필요한 값을 가져오고,

BirdieBuddy에서 사용할 수 있는 형태로 저장했습니다.

그리고 마지막에 터미널에 나온 문장이 이것이었습니다.

```text
Courses: 345 saved.
```

**345개의 코스 레코드가 저장됐습니다.**

## 문제는 "가져왔다"가 끝이 아니었다

345라는 숫자를 보고 처음에는 성공했다고 생각했습니다.

그런데 데이터를 자세히 보기 시작하면서 새로운 문제가 생겼습니다.

웹에서 값을 가져오는 것과

**올바른 데이터를 가져오는 것은 전혀 다른 문제**였습니다.

어떤 골프장은 아주 깔끔했습니다.

```text
Course Rating: 69.8
Slope Rating: 124
Par: 70
```

그런데 어떤 데이터를 열어보면 상황이 달랐습니다.

```text
Rating: 0
Slope: 0
Par: 0
Distance: 0
```

아주 깔끔합니다.

**쓸 수 없다는 점만 빼면요.**

일부 코스는 제가 예상했던 데이터가 존재하지 않았고,

페이지 구조나 데이터 형태가 다른 경우도 있었습니다.

어떤 경우에는 정상적인 코스 정보 대신 placeholder처럼 0으로 채워진 값이 들어오기도 했습니다.

이때부터 스크래퍼의 목표도 조금 바뀌었습니다.

처음에는

> "데이터를 가져오자."

였다면,

나중에는

> "가져온 데이터가 정말 사용할 수 있는 데이터인지 확인하자."

가 됐습니다.

두 문장은 비슷해 보이지만 구현할 때는 꽤 다릅니다.

웹 스크래핑을 하면서 가장 크게 느낀 것도 이것이었습니다.

> **페이지를 읽는 데 성공했다고 데이터 수집에 성공한 것은 아니다.**

## Python에서 C#으로

BirdieBuddy 본체는 **C#/.NET**으로 만들기 시작했습니다.

반면 골프장 데이터 수집은 **Python + Playwright**로 구현했습니다.

처음부터 모든 것을 하나의 언어로 만들 필요는 없다고 생각했습니다.

웹 데이터를 가져오는 작업은 Python으로 처리하고,

수집한 데이터를 JSON 형태로 정리한 다음,

BirdieBuddy의 모델에서 사용할 수 있도록 가져오는 구조로 만들었습니다.

```text
Golf New Zealand
       ↓
Python + Playwright
       ↓
     JSON
       ↓
Application Models
       ↓
   BirdieBuddy
```

이 과정에서 단순히 데이터를 가져오는 것보다

**가져온 데이터를 어떻게 표현할 것인가**도 중요해졌습니다.

BirdieBuddy에는 `Course`, `CourseHole`, `CourseTee`, `Round`, `Hole` 같은 모델이 있습니다.

예를 들어 `Round`는 어떤 Tee에서 플레이했는지를 알아야 하고,

각 `Hole`에는 실제 플레이 결과가 들어갑니다.

단순히 스코어만 저장하는 것이 아니라,

GIR이나 Fairway Hit 같은 기록도 남길 수 있게 만들었습니다.

그러다 보니 validation도 필요해졌습니다.

홀 번호는 정상적인 범위 안에 있어야 하고,

Par도 현실적인 값이어야 하고,

스코어는 0보다 커야 합니다.

그리고 Par 3에서는 Fairway Hit를 기록하는 것이 의미가 없습니다.

이제는 잘못된 스코어를 저장하려고 하면 코드가

> "그건 골프 규칙상 이상한데?"

라고 저를 막습니다.

## 그리고 결국 iOS 앱까지 왔다

처음에는 데이터 모델과 기록 기능을 만드는 것부터 시작했지만,

프로젝트를 계속 진행하면서 BirdieBuddy는 점점 실제로 제가 사용할 수 있는 앱 형태에 가까워졌습니다.

웹앱을 거쳐 지금은 **iOS 쪽 개발도 거의 끝나고 검증하는 상태**입니다.

라운드를 기록하고,

코스를 선택하고,

홀별 데이터를 입력하고,

내 기록을 확인하는 기본적인 흐름은 대부분 만들어졌습니다.

처음에는 단순히

> "내 골프 기록을 직접 관리해보자."

정도의 생각이었는데,

지금은 이미 일이 커질대로 커져버려서

> "App Store에 출시해서 주변 사람들 써보라고 해야겠다"

가 되어버렸습니다.

그런데 여기서 또 하나의 현실적인 문제가 등장했습니다.

**Apple Developer Program**입니다.

App Store에 제대로 출시하려면 Apple Developer Program에 가입해야 하고,

매년 비용을 내야 합니다.

사이드 프로젝트로 시작한 앱에 실제로 돈까지 내고 출시할 것인가.

지금은 그걸 조금 고민하고 있습니다.

개발은 거의 끝났는데,

**마지막 단계가 코드가 아니라 결제 버튼일 줄은 몰랐습니다.**

물론 언젠가는 출시해보고 싶습니다.

직접 만든 앱을 실제 App Store에서 받아보는 경험도 해보고 싶고,

무엇보다 제가 아닌 다른 골퍼가 BirdieBuddy를 사용해보는 것도 꽤 재미있을 것 같습니다.

다만 지금은

> "내가 매년 돈을 내면서까지 이 앱을 유지할 것인가?"

를 생각해보는 중입니다.

코드는 거의 완성됐는데,

**출시 여부는 아직 `boolean?` 상태입니다.**

## 직접 만드는 이유

사실 골프 기록 앱은 이미 세상에 많습니다.

굳이 제가 하나 더 만들 필요는 없습니다.

그런데 BirdieBuddy는 제가 실제로 사용하는 앱을 직접 만들어본다는 점에서 다른 프로젝트와 조금 다른 재미가 있습니다.

예를 들어 이런 기록이 있다고 해봅시다.

```text
Par 4
Score: 5
GIR: false
Fairway Hit: true
```

이걸 보면 무슨 일이 있었는지 대충 상상이 됩니다.

티샷은 살았습니다.

그런데 세컨샷이 그린에 못 올라갔습니다.

결국은 보기.

**굳이 앱까지 만들어서 저의 못난 플레이를 데이터베이스에 영구 보존하고 있습니다.**

하지만 기록이 쌓이면 단순히 평균 스코어만 보는 것보다 더 많은 것을 확인할 수 있습니다.

내가 실제로 어디서 타수를 잃는지,

GIR이 얼마나 되는지,

티샷이 문제인지,

아이언이 문제인지,

숏게임이 문제인지.

그리고 언젠가는 골퍼라면 누구나 한 번쯤 궁금해하는 아주 중요한 질문에도 답할 수 있을 겁니다.

> "정말 장비 문제였을까? 아니면 내 실력이 문제였을까?"

## 만들면서 배운 것

처음에는 BirdieBuddy를 프로그래밍을 더 연습해보기 위한 프로젝트 정도로 생각했습니다.

그런데 만들다 보니 꽤 다양한 문제를 만나게 됐습니다.

API를 찾아보고,

실제로 연결해보고,

원하는 데이터가 없어서 다른 방법을 찾고,

Playwright로 웹 데이터를 가져오고,

JSON으로 정리하고,

도메인 모델을 설계하고,

잘못된 값을 막기 위한 validation까지 추가했습니다.

그리고 결국 iOS 앱까지 만들게 됐습니다.

이 과정에서 한 가지를 꽤 확실하게 배웠습니다.

> **실제 데이터는 내가 예상한 것만큼 친절하지 않다.**

학교에서 주는 예제 데이터는 항상 예쁩니다.

ID도 있고,

이름도 있고,

필요한 값도 전부 들어 있습니다.

실제 데이터는 그렇지 않았습니다.

값이 없기도 하고,

예상과 다른 형태로 들어오기도 하고,

어떤 데이터는 정상인지 아닌지부터 확인해야 합니다.

API가 있다고 해서 내가 원하는 데이터가 있는 것도 아니고,

웹페이지에 데이터가 있다고 해서 그대로 사용할 수 있는 것도 아니었습니다.

결국 데이터를 **가져오는 것**, **정리하는 것**, **검증하는 것**, 그리고 **애플리케이션의 모델로 표현하는 것**은 전부 다른 문제였습니다.

그리고 이상하게도 과정은 힘들었지만 이런 문제를 하나씩 해결하고 나면 꽤 뿌듯했습니다.

다음에 골프를 치다가 또

> "이런 기능 있으면 좋겠는데?"

라는 생각이 들어서 기능 추가를 하다보면 또 어떤 고생을 할지 모릅니다.

하지만 그럼에도 불구하고 저는 아마 계속해서 만들어볼겁니다.

실패하고, 잘 만든줄 착각하고, 또 에러가 나도, 실패에서 배우는 제가 되길 원하니까요.
